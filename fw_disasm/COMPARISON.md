# Сверка с анализом `agamez/hg-uv98-firmware`

Сравнение разбора `V1.2_211026` (`fw/REPORT.md`) с 
исследованием [agamez/hg-uv98-firmware](https://github.com/agamez/hg-uv98-firmware)

---

## 1. Совпадает (независимо подтверждено)

| Утверждение upstream | Подтверждение в V1.2 |
|---|---|
| База линковки приложения `0x08004000`, бутлоадер `0x08000000–0x08003FFF` в образе отсутствует | reset-вектор `0x080446C9` → файл `0x0406C8` = `nop.w; nop.w; bl 0x08042A10`; все пулы/векторы согласуются только с этой базой |
| 76 записей вектор-таблицы, MSP `0x20006780` | `out/vector_table.txt`: 76 записей, SP `0x20006780` |
| Reset-обработчик vendor-ом «нейтрализован» (`nop.w; nop.w; bl`) | `SYS_RESET 0x080446C8` подтверждён байт-в-байт |
| PendSV и SysTick — реальный код, а не заглушки | PendSV `0x0802B256`: `cpsid i; mrs r0, faultmask; stm r4-r11`; SysTick `0x0802BDA4` |
| Вычищенный BEEF-модуль ≈21 КБ сразу после кода приложения | V1.2: файл `0x29B9C–0x2EE02` (≈21 КБ) — та же граница, тот же паттерн `0xBEEF` |
| uC/OS-II, 7 задач, UI-задача в MASTER-режиме | `OSTaskNameSet 0x08028A6C`, `OSStart 0x0802B392`, UI-петля `0x0802D178` — все три адреса попадают в декодированный код V1.2, соответствующие функции имеют идентичные с KT тела (см. `out/crossref.csv`) |
| AT-протокол с 8051 (`$A00`, `$A01`, `AT…`), USART 9600 8N1 | строки `"$A00,"`/`"$A01,"` — linked `0x080407A4`/`0x080407AC` (KT: `0x0804081C`/`0x08040824`) |
| Диспетчер AT-команд, мост протокола, state machine, «каждый 17-й проход» | их `0x08014128`, `0x08013E58`, `0x08014302`, `0x08012D24` — **точные начала функций** и в KT, и в V1.2, тела идентичны |
| Шрифт CJK/ASCII идёт по SPI из внешней флеш, в образе шрифта нет | подтверждено: зона `0x08004130+` — не шрифт (см. §3) |
| IRQ 37/38 = GPS-порт и порт 8051 | `idx 53` (`IRQ 37`, GD32 «USART0») → `0x0802B0FD`; `idx 54` (`IRQ 38`, GD32 «USART1») → `0x0802B107` |

### Количественная сверка их реестра покрытия

`docs/COVERAGE.md` upstream содержит **685** уникальных адресов (это linked-адреса,
а не label). Проверка «попадает ли адрес в декодированный код» на моём листинге:

| Сборка | в коде | точно на начале функции | не декодируется |
|---|---|---|---|
| V1.0.1_190619-KT (их база) | 574 / 685 (84 %) | 68 | 111 |
| V1.2_211026 | 569 / 685 (83 %) | 214 | 116 |

То есть их адресное пространство в V1.2 сохраняется почти полностью: поздняя
сборка делает локальные вставки, но не перетасовывает функции.

## 2. Расхождения и устаревшие места в их документации

1. **`docs/FIRMWARE_INVENTORY.md`: «V1.2_211026 — ❌ Not available».**
   Образ доступен (архив `Lanchonlh HG-UV98 Radio Firmware V1.2_211026.zip`,
   507 904 Б, SHA-256 `05fa326b…88a7c6`) и полностью разобран здесь.
   Диф с KT: **522 из 673 функций с идентичным телом**, типичный сдвиг `+0x48`
   (202 функции) или `+0x4C` (155); строк `+148 / −243`.

2. **`README.md`: «60 IRQ trampolines (stripped in all distributed images; only the
   structure is known)» — неверно.**
   В *обеих* сборках лестница трамплинов присутствует физически:
   `0x0802AF8A…0x0802B1E0`, 60 стабов с шагом **10 байт**, каждый —
   `ldr r0,[pc]; b диспетчер`, диспетчер `FUN_0802B1E2`, RAM-таблица указателей
   `0x20004AA4`, счётчик активных IRQ `0x2000516B`. Проверено и в KT
   (`out_v101/…lst`, строка 52792) и в V1.2. Значит `startup.c` в их
   reconstruction можно «раскрыть» из образа, а не держать как SCAFFOLD.
   (В поздних сессиях их RESEARCH_LOG это уже исправлено — но README остался старым.)

3. **Адреса шаблонов маяка.** В доке: `"$B%02d"`/`"$C%02d"` по linked
   `0x08043B08`/`0x08043B14`. Фактически в KT строки лежат по `0x08043C0C`/
   `0x08043C18`, в V1.2 — по `0x08043B34`/`0x08043B40` (сдвиг `0x104`). Похоже,
   в доке процитирован адрес соседней структуры, а не строки.

4. **«vtable меню в `0x08040AEC`, шаг `0x10`: [key_index, press, second, once_flag]».**
   Воспроизвести не удалось: по linked `0x08040AEC` (файл `0x3CAEC`) в KT лежит
   таблица с шагом 16, но с полями вида `{3, 1, 0x08016799, …}` —
   layout не соответствует описанному; в V1.2 этот регион вообще другой.
   Утверждение оставляю как **непроверенное** (возможен другой базис/другая таблица).

5. **Смешение конвенций адресов** — главный источник путаницы при сверке:
   проза даётся в label, реестр `COVERAGE.md` и REA — в linked. Всё, что ниже,
   я пересчитывал `+0x4000`.

## 3. Что добавляет разбор

1. **Разобран образ, которого у них нет** — `V1.2_211026` (ноябрь 2021,
   последняя известная). Полный листинг, 673 функции, 1 625 строк, диф с KT.

2. **Механика прерываний**: лестница стабов → индекс → RAM-таблица `0x20004AA4`
   → функции-обработчики, плюс счётчик `0x2000516B`. У них IRQ-слой помечен как
   неизвестный/вычищенный.

3. **Закрыт их открытый пункт O5 («Font/bitmap assets, format analysis pending»)**
   для зоны `0x08004130`. Это **не** знакогенератор и не шрифт, а полноэкранная
   **заставка 160×128, RGB565, старший байт первым, 40 960 Б**:

   ```
   0801B7E2  mov.w r0, #0xa000     ; 40960 = 160*128*2
   0801B7E6  str   r0, [sp, #4]    ; len
   0801B7E8  ldr   r0, [pc]        ; = 0x08004130
   0801B7EA  str   r0, [sp]        ; src
   0801B7EC  movs  r3, #0xa0       ; h = 160
   0801B7EE  movs  r2, #0x80       ; w = 128
   0801B7F0  movs  r1, #0
   0801B7F2  movs  r0, #0
   0801B7F4  bl    FUN_0801D368
   ```

   `FUN_0801D368` ставит окно, шлёт команду `0x2C` и стримит `len/2` 16-битных
   пикселей. Рендер (`out/v_be_160x128.png`) — заставка **«LANCHONLH /
   FM DUAL BANDER+APRS»**. Панель 128×160, картинка выводится повёрнутой.
   Это же объясняет, почему «шрифта в образе нет»: шрифт действительно во
   внешней SPI-флеш, а `0x08004130` — картинка.

4. **Список изменений KT → V1.2** (у них его нет, т.к. нет образа):
   `out/diff_strings.txt` (+148/−243) — новая нумерация меню (`01.`, `03.`, `04.`,
   `06.`), APRS-экраны, шкала дБ, двуязычные подписи; `out/diff_functions.csv` —
   522 совпадающие функции и их сдвиги.
