# Дизассемблирование прошивки Lanchonlh HG-UV98 — Main MCU, V1.2_211026

Полный реверс-инжиниринг образа `Lanchonlh HG-UV98 Radio Firmware V1.2_211026.zip`
из репозитория [dkxce/HG-UV98](https://github.com/dkxce/HG-UV98/tree/master/Software).
Да, прошивка дизассемблирована целиком: получен аннотированный листинг, таблица
символов, карта памяти и отчёт об отличиях от предыдущей публичной сборки
(V1.0.1_190619-KT).

## 2. Адресация — читать обязательно

В образе **две системы адресов**, и это главный источник путаницы при анализе:

* файл линкован под **`0x08004000`** (не под `0x08000000`). Это доказывается тем,
  что значения векторной таблицы и литеральных пулов попадают в осмысленные места
  только при вычитании `0x4000`: Reset `0x080446C9` → файловое смещение `0x406C8`,
  где лежит `nop.w; nop.w; bl` (заглушка сброса от вендора);
* загрузчик `0x08000000–0x08003FFF` в `.bin` **не входит** — отсюда и размер
  ровно 512 КБ − 16 КБ;
* **в листинге `out/*.lst` все адреса — реальные адреса устройства**
  (файловое смещение + `0x08004000`), поэтому они совпадают со значениями в
  векторной таблице и в пулах, и их можно сравнивать с даташитом/отладчиком.

> В документации проекта `agamez/hg-uv98-firmware` (RESEARCH_LOG/COVERAGE) принята
> другая конвенция — «label = файл + 0x08000000». Их адреса на `0x4000` меньше
> здешних. При сверке это нужно учитывать.

|---|---|---|

| `0x3E000–0x42BD0` | `0x08042000–0x08046BD0` | стартап/`__main`, бут-стаб, `printf`-подобная библиотека **вперемешку** со строковыми таблицами (ASCII + GB2312) |

Границы кодовых зон определены эмпирически (плотность прологов `push {…,lr}`,
доля успешных декодирований, цели ветвлений), а не взяты из документации.

## 4. Что сделано и с каким результатом

Инструмент: `tools/re_disasm.py` (capstone 5.x, Python). Так как прошивка
**таблично-управляемая** (меню и обработчики вызываются через таблицы указателей),
обход только по графу вызовов покрывает <10 % кода. Поэтому применён
пересинхронизирующий линейный проход с исключением:

* векторной таблицы,
* строковых записей (ASCII + GB2312, с проверкой NUL-терминатора),
* заливок `0xFF` / `0x00` / `0xBEEF`,
* литеральных пулов, на которые реально ссылаются `ldr rX, [pc, #imm]`
  (кандидат принимается только если слово похоже на данные: указатель в Flash/RAM,
  периферийный адрес, малая константа).

Плюс ручной fallback для `MRS/MSR` с системными регистрами, которые эта сборка
capstone отказывается декодировать (`cpsid i; mrs r0, faultmask` в PendSV).

Результат по образу V1.2_211026:

| Метрика | Значение |
|---|---|
| Декодировано инструкций | **51 905** |
| Байт кода | **132 162** (≈82 % доступных кодовых зон) |
| Найдено функций | **673** |
| Строк | **1 625** (1 014 ASCII + 611 GB2312) |
| Литеральных пулов | **1 042** |
| Уникальных IRQ-векторов | 60 из 60 |
| Аннотированный листинг | ≈62 тыс. строк, 3.8 МБ |

## 5. Что видно в коде

### 5.1 Векторная таблица и цепочка запуска

```
[ 0] MSP   = 0x20006780
[ 1] RESET = 0x080446C9 -> 0x080446C8:  nop.w; nop.w; bl 0x08042A10
```

`0x08042A10` — бут-стаб (`FUN_08042A10`), который делает
`bl 0x08042A2E` → `cmp r0,#0` → `bl 0x0804293C` → `bl 0x0802D15C` (инициализация)
→ `bl 0x08042A32` → `b.w 0x08042A38` и далее бесконечный главный цикл
`LAB_08042A3A` с вызовом `FUN_0802D6DC`. Сами `nop.w` перед `bl` — вендорская
«заглушка»: кода инициализации стека и вызова `__main` в образе нет, это же
поведение отмечено и для более ранних сборок.

Системные обработчики (все в образе, все декодируются):

| Вектор | Адрес | Что это |
|---|---|---|
| NMI / HardFault / MemManage / BusFault / UsageFault | `0x080446BC…0x080446C6` | короткие `b .`-стабы |
| PendSV | `0x0802B256` | переключение контекста uC/OS-II: `cpsid i; mrs r0, faultmask; stm r4–r11; сохранение SP` |
| SysTick | `0x0802BDA4` | `push {r4,lr}; bl 0x0802B21C; инкремент счётчика 0x2000516B; bl 0x0802B44A` — тик ОС |

### 5.2 IRQ: 60 одинаковых стабов + диспетчер в RAM

Все 60 IRQ-векторов (`0x0802AF8A … 0x0802B1E0`, шаг ровно 10 байт) — лестница
одинаковых стабов вида

```
push {r7, lr}
movs r0, #<номер IRQ>
bl   0x0802B1E2        ; диспетчер
pop  {r0, pc}
```

Диспетчер `FUN_0802B1E2`:

```
ldr  r0, =0x20004AA4      ; таблица из 60 указателей в RAM
cmp  r4, #0x3c            ; 60
bhs  ...
ldr.w r0, [r0, r4, lsl #2]
blx  r6                   ; вызов установленного обработчика
```

Счётчик вызовов — байт `0x2000516B`. Таблица в RAM заполняется через
`FUN_0802AF26` — это `NVIC_SetVectorTable`:

```
r2 = (r1 & 0x1FFFFF80) | r0 ; *(uint32_t*)0xE000ED08 = r2 ; bx lr
```

То есть приложение переносит таблицу векторов в RAM (`VTOR`) и работает через
свою таблицу обработчиков — типичная схема для uC/OS-II с приоритетными ISR.

### 5.3 Версия и идентификатор модели

Экран «Version» (`FUN_08019696`) рисует подписи и строку версии общим
текстовым выводом `FUN_0801CB94` (350 вызовов — самая вызываемая функция,
это отрисовка строки):

```
08019804  ldr.w r2, [pc, #0xb60]   ; "V1.2_211026"
```

Рядом, в `0x08045A4C`, лежат `"V1.0.1"` и `"IiNHSG0NNiNHSG0NP3107"`
(ссылка из `0x0802D8EE`) — тот самый идентификатор **P3107**, по которому CHIRP
различает модели HG-UV98; в отчётах фигурировало, что у V1.2_210517 строка другая
(`P3LL`), здесь — `P3107`.

### 5.4 Обмен с 8051-сопроцессором APRS

Строки-префиксы протокола обмена с APRS-CPU (`$A00,` / `$A00`) находятся в
`0x08013E70` и `0x080239DC`; обработчик начала кадра сравнивает 5-байтовый
префикс и разветвляется по типу предложения. Это согласуется с описанным в
документации протоколом `$A09/$A10/$A11/$A50/$A51`, `$E01/$E02/$E00`, `AT11/AT12`.

### 5.5 Периферия (по обращениям к регистрам и литеральным пулам)

`GPIOA (63)`, `GPIOC (45)`, `GPIOB (32)`, `RCU (20)`, `SCB (10)`, `SysTick (7)`,
`USART0 (5)`, `USART1 (5)`, `TIMER2 (4)`, `TIMER0 (3)`, `SPI0 (3)`, `SPI1 (3)`,
`I2C0`, `ADC0`, `GPIOD`. Профиль совпадает с GD32F103RE и с описанием железа:
LCD по SPI, EEPROM/датчики по I2C, трансиверы AT1846S по 3-wire, UART — на 8051-CPU
и на консоль/Bluetooth. Обращений к CAN/USB в живом коде нет (стабы есть, как у
любого GD32F103).

### 5.6 Графика: заставка (а не шрифт)

На зону `0x08004130` есть ровно **одна** ссылка из кода — `0x0801B7E8`, в функции
экрана приветствия, которая вызывает блиттер:

```
0801B7E2  mov.w r0, #0xa000      ; 40960 = 128*160*2
0801B7E6  str   r0, [sp, #4]     ; длина в байтах
0801B7E8  ldr   r0, [pc]         ; = 0x08004130, источник
0801B7EA  str   r0, [sp]
0801B7EC  movs  r3, #0xa0        ; h = 160
0801B7EE  movs  r2, #0x80        ; w = 128
0801B7F0  movs  r1, #0
0801B7F2  movs  r0, #0
0801B7F4  bl    FUN_0801D368     ; окно + cmd 0x2C + поток пикселей
```

`FUN_0801D368(x, y, w, h, src, len)` ставит окно, посылает команду `0x2C`
(memory write, семейство ILI9341/ST7735 — совпадает с их «display.c: cmd 0x2C»)
и в цикле отдаёт `len >> 1` 16-битных пикселей: `while (i < len/2) { byte(src[2i]);
byte(src[2i+1]); }`.

Значит зона — **не знакогенератор, а полноэкранная картинка**: 160×128, RGB565,
старший байт первым, 40 960 Б. Рендер подтверждает: это заставка
**«LANCHONLH / FM DUAL BANDER+APRS»** (сине-голубая графика, белый фон).
Панель 128×160 — картинка выводится повёрнутой на 90°.

Готовые PNG: `out/v_be_160x128.png` (правильная ориентация) и
`out/splash_08004130.png` (128×160, как передаётся в контроллер).

Шрифт (CJK/ASCII) в образе **отсутствует** — он читается по SPI из внешней
флеш, как и описано в документации проекта `agamez/hg-uv98-firmware`.
Иконки — отдельная зона ≈`0x08038000+`.

## 6. Отличия V1.2_211026 от V1.0.1_190619-KT

Сравнение с последней публичной сборкой (`v101/V1.0.1_190619-KT.bin`,
SHA-256 `5a2a42e2…20dbce`, идентичная разметка):

| Метрика | V1.0.1_190619-KT | V1.2_211026 |
|---|---|---|
| Инструкций | 51 892 | 51 905 |
| Функций | 675 | 673 |
| Байт кода | 132 114 | 132 162 |
| Совпадающих по телу функций | — | **522 из 673** |
| Строк (уник.) | 1 403 | 1 308 |

Типичный сдвиг адресов совпадающих функций: **+0x48** (202 функции) и
**+0x4C** (155) — то есть код почти тот же, вставки небольшие и локальные.
54 функции совпадают без сдвига вообще.

Содержательные изменения (по строкам; полный список — `out/diff_strings.txt`):

* меню переведено на двухзначную нумерацию с точкой:
  `01.LOCAL SETUP`, `02.Fixed site`, `03.GPS SETUP`, `03 SYMBOL table`,
  `04.BEACON SETUP`, `05.BEACON MODE`, `06.DIGI SETUP`, `07.Bluetooth`,
  `08.Advanced`, `09.Version`, `11.Meteorological`;
* подписей старого стиля (`1 Call Sign`, `2 SSID`, `4 Beacon Setup`, …) в V1.2
  больше нет;
* добавлены экраны APRS-настроек: `01 APRS RX CH`, `02 APRS TX CH`,
  `01 DATA OUTPUT A/B`, `02 DIGI1 ON/OFF`, `03 DIGI1 NAME`, `04 DIGI2 ON/OFF`,
  `05 DIGI2 NAME`, `06 DIGI TX WAIT`, `06 MIC-E ON/OFF`, `07 MIC-E TYPE`,
  `08 PATH 1`, `09 PATH 1 COUNT`, `07 Remote password`;
* добавлена шкала уровней: `0 db`, `-1.5 db`, `-3.0 db`, `-4.5 db`, `-6.0 db`,
  `-7.5 db`, `-9.0 db`, `-10.5 db`;
* добавлены смешанные англо-китайские подписи: `03.GPS 设置`, `06 MIC-E启用`,
  `2.硬件版本`, `硬件版本:`;
* добавлены пункты `06 SFT_D`, `07 VOX_GRD`, `08 CH A MUTE`, `09 CH B MUTE`,
  `POWER AUTO ZERO`, `Crash site`, `No. Diam'd`;
* строка версии `V1.2_211026` и остаток `V1.0.1` рядом с `P3107`.

Удалённые строки в основном относятся к «хвосту» KT-образа (`0x08042BD0+`),
которого в V1.2 физически нет (в V1.2 там `0xFF`), плюс старые подписи меню.

## 7. Ограничения (честно)

1. **Это дизассемблер, а не декомпилятор.** Имена `FUN_/LAB_/STR_` — автоматические;
   по поведению опознаны только якоря из §5. Полноценная декомпиляция — в Ghidra
   (она в системе не установлена; импортировать `.bin` нужно с базой **`0x08004000`**,
   имена подтянуть из `out/symbols.csv`).
2. **Зона `0x0802DB60–0x08032E02` (~21 КБ) вычищена производителем** — там только
   заливка `0xBEEF`/`0x9EEF`. Восстанавливать нечего; это удалённый модуль.
3. Графические зоны (заставка, иконки) не дизассемблировались — только помечены
   как данные; формат заставки восстановлен в §5.6. Внутри кодовых зон возможны
   редкие локальные рассинхронизации на
   стыке функции и пула (в листинге они видны как `.byte`).
4. Загрузчик `0x08000000–0x08003FFF` в образе отсутствует, поэтому полный цикл
   «включение → приложение» по одному этому файлу не восстанавливается.
5. Ничего не запускалось на железе и в эмуляторе: все выводы — статические.

## 9. Сверка с agamez/hg-uv98-firmware

Подробно — в `fw/COMPARISON.md`, машинная таблица — `fw/out/crossref.csv`.

**Совпадает:** база `0x08004000`; 76 векторов и MSP; ставший `nop.w; nop.w; bl`
reset; реальные PendSV/SysTick; вычищенный BEEF-модуль ≈21 КБ
(`0x29B9C–0x2EE02`); uC/OS-II; AT-протокол с 8051 (`$A00`/`$A01`); «шрифт во
внешней SPI-флеш»; IRQ 37/38 = GPS-порт и порт 8051. Их реестр из 685 адресов
(`docs/COVERAGE.md`, linked-конвенция) попадает в декодированный код на 569/685
(83 %) — адресное пространство V1.2 почти не сместилось.

**Устарело/неточно у них:**

- `FIRMWARE_INVENTORY.md` числит V1.2_211026 как «not available» — образ есть и
  разобран здесь (522/673 функции с идентичным телом, сдвиг `+0x48`);
- «60 IRQ-трамплинов вырезаны во всех сборках» — неверно: лестница 60 стабов
  `0x0802AF8A…` (шаг 10 Б) и диспетчер `0x0802B1E2` есть и в KT, и в V1.2;
- адреса шаблонов `"$B%02d"`/`"$C%02d"` сдвинуты на `0x104` относительно факта;
- таблица меню `0x08040AEC` в заявленном формате не воспроизводится
  (не подтверждено ни в KT, ни в V1.2).

**Добавлено мной:** механика IRQ (стабы → индекс → RAM-таблица `0x20004AA4`),
формат заставки (§5.6 — закрывает их пункт O5), диф KT → V1.2 и листинг образа,
которого у них нет.
